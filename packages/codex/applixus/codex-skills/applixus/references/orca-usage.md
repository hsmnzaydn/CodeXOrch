# Orca-only Codex worker and reviewer

Write a short /tmp brief: paraphrase symptoms and state expected behavior. From its own terminal the Lead first binds a Run with `orca orchestration run-create --objective "<goal>"`, then starts `orca orchestration worker-start --spec <short brief> --worktree current --agent codex --model codex-sub-model`; use `codex-sub-high` for hard work. The worker edits directly in the user's checkout on the current branch (main is fine), commits unless the project pack forbids it, runs ONE quick direct check of changed behavior and reports observations. The applicable project pack's git policy wins.

Wait for worker_done with `orca orchestration check --wait --types "worker_done,escalation,question" --timeout-ms 90000 --json`; if it does not arrive, read the result with `orca orchestration worker-read --dispatch <id> --limit 20` and `orca orchestration worker-show --dispatch <id>`. Answer questions with `orca orchestration reply --id <msg_id> --body "<answer>"`; process the whole delivery, then pass `--ack <delivery_id>` on the next check. An empty (timed out) wait is a checkpoint, not a failed worker. Once settled, inspect `orca orchestration worker-show --dispatch <id>`, then `orca orchestration worker-release --dispatch <id>`. Start a SEPARATE read-only Codex reviewer the same way with `review-model`. Reviewer target: the commit by default; for no-commit projects the recorded base SHA plus the full working-tree change set (tracked diff vs base, staged, and untracked files with contents). No commit is expected there. Review against expected behavior. Give worker and reviewer the same git policy, base SHA and short acceptance list (AC-1, AC-2, ...). Nobody edits the candidate during review. If it finds a problem, start a fix worker and review again. Orca owns start, completion, release and worktree; the toolkit adds no lifecycle code.

Pass `--timeout-ms 120000` (bounds Orca readiness/delivery wait, not task length). Check progress with `orca orchestration worker-show --dispatch <id>` and `orca orchestration worker-read --dispatch <id> --limit 20` (rows), continuing with `--cursor <cursor>`; output stays readable after worker-release. A worker that looks silent may be waiting on a question: check its inbox and worker-read and answer it. Never stop a worker for silence alone; report observed state. If worker-read shows an update prompt, tell the user to update Codex or answer the prompt instead of retrying. Never duplicate an uncertain start or timeout; inspect the same worker.
On `agent_readiness` timeout, run `worker-show` once (the agent may still boot); if the brief never arrived, report BLOCKED with the observed state; no retry.

If Codex exits with "Cannot use the shared background server" because the session requires `api_key_model_discovery` to be disabled, its diagnostic directs rerunning the same command with `--no-daemon`, preserving `resume` or `fork` and their arguments. Do not mutate Codex config or daemon settings. For an Orca-dispatched worker, inspect the same Dispatch with `worker-show` and `worker-read` and let native Orca recovery own any relaunch; do not manually start a second worker or retry an uncertain/live Dispatch.

After a lost or uncertain mutation response, run `orca orchestration request-show --request <requestId>`. For completed/pending, repeat the SAME command with `--retry-request <requestId>` (replays the request, no second worker). Absent is not proof nothing happened: inspect `orca orchestration worker-show --dispatch <id>`, never start a duplicate. Do not duplicate accepted work after a timeout. Redo only a genuinely failed, settled worker with `orca orchestration worker-start --task <task_id> --retry-of <dispatch_id> --worktree current --agent codex --model codex-sub-model`.

Cleanup inventory: `orca worktree ps`, `orca orchestration worker-list --run <run> --terminal-state reclaimable` and `orca orchestration worker-list --run <run> --terminal-state release_unknown`; release only your own settled workers. `worker-abandon` does not stop a process; never use it for silence.
For Orca command details run `orca skills get orchestration` (version-matched) instead of guessing flags.

If Orca is unavailable, report BLOCKED plainly and tell the user to start Orca; no fallback. Lead Read/Grep/Glob discovery is allowed without a scout prerequisite; every Lead Agent call and product Edit/Write stay denied. Never mutate product files through Lead Bash or disable the guard. Review/inceleme/kontrol stays readonly. No test suite or fix-forward test loop. A toolkit release is confirmed with one quick direct check in a fresh session.

## Big job: parallel lanes

The commit-based lane and integration recipe below applies only when the project pack permits commits. For no-commit projects, keep the current-checkout route serial under the pack's git policy and hand off the frozen working-tree change set instead.

Single job: keep `--worktree current` as the default. A big job has 2+ independent parts with no ordering dependency that touch DIFFERENT files: start each part at once with `orca orchestration worker-start --spec <short brief> --worktree new-child --name <part> --base-branch main --agent codex --model codex-sub-model --timeout-ms 120000`, giving each lane its own short acceptance list (AC-1, AC-2, ...). Orca readiness currently allows max 4 parallel lanes. Each worker commits on its own child branch; it does not touch main or share the user's checkout/index. Dependent parts or shared files stay serial: finish one lane before starting the next, or use the previous lane's branch as the next part's `--base-branch`. A failed lane does not block the other lanes; redo only that part, inspecting uncertain outcomes before retrying.

After the lanes finish, start ONE integrator Codex worker with `--worktree current`: it takes the lane commits onto main in order with rebase/cherry-pick, resolves conflicts, runs ONE quick direct check and commits. Main requires linear history, no merge commits. The Lead never writes to the product or rebases through Bash. A SEPARATE read-only Codex reviewer reviews the integrated commit range on main against each lane's AC list; a problem goes to a fix worker, then review again. The same pattern allows one parallel read-only reviewer per lane, without replacing the integrated review. Only after the integrator reports the commits are on main, release each lane with `orca orchestration worker-release --dispatch <id>` and remove its worktree with `orca worktree rm --worktree <lane-worktree>`. Use native Orca and git commands only; no toolkit code/command/lifecycle layer.

Commits/PRs fixing an issue include Fixes #n. Preserve tenant scope, redact secrets, and obtain recorded owner approval before live external operations with real credentials.
