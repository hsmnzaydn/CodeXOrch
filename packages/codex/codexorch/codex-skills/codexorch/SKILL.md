# CodeXOrch toolkit

Never build a toolkit layer that re-implements what Orca, Codex or git/GitHub already do natively (lifecycle, waiting, receipts, resume, cleanup, release, promotion, verdict parsing); use the native command and put the guidance in text.

Lead orchestrates only. Read/Grep/Glob are allowed for diagnosis; product Edit/Write and every Lead Agent call stay denied. Workers are exempt. Never mutate product files through Lead Bash or disable the guard.
Lead may write temporary briefs, reports and Codex project documentation.
For security analysis requests ("güvenlik analizi yap", "security scan"), follow [on-demand Strix security scanning](references/security-scan.md).

## Orca-only worker route

Write a short /tmp brief: paraphrase symptoms and state expected behavior. Put raw logs in a separate evidence file labeled as captured earlier (source command and date), not output of the worker's own commands, and link it from the brief. From its own terminal the Lead first binds a Run with `orca orchestration run-create --objective "<goal>"`, then starts `orca orchestration worker-start --spec <short brief> --worktree current --agent codex --model codex-sub-model`; use `codex-sub-high` for hard work. The worker edits directly in the user's checkout on the current branch (main is fine), commits unless the project pack forbids it, runs ONE quick direct check of changed behavior and reports observations. Pack means the applicable project pack; its git policy wins.
Wait for worker_done with `orca orchestration check --wait --types "worker_done,escalation,question" --timeout-ms 90000 --json`; if it does not arrive, read the result with `orca orchestration worker-read --dispatch <id> --limit 20` and `orca orchestration worker-show --dispatch <id>`. Answer questions with `orca orchestration reply --id <msg_id> --body "<answer>"`; process the whole delivery, then pass `--ack <delivery_id>` on the next check. An empty (timed out) wait is a checkpoint, not a failed worker. Once settled, inspect `orca orchestration worker-show --dispatch <id>`, then use `orca orchestration worker-release --dispatch <id>`. Start a SEPARATE read-only Codex reviewer the same way with `review-model`. Reviewer target: the commit by default; for no-commit projects the recorded base SHA plus the full working-tree change set (tracked diff vs base, staged, and untracked files with contents). No commit is expected there. Review against expected behavior. Give worker and reviewer the same git policy, base SHA and short acceptance list (AC-1, AC-2, ...). Nobody edits the candidate during review. The reviewer marks each AC Met/Unmet/Unverified with evidence, including required callers, states or variants the diff did not touch only when the ticket or linked comments request them; missing evidence is Unverified, never Met. See references/handoff.md. If it finds a problem, start a fix worker, then review again. Orca owns start, completion, release and worktree; no toolkit lifecycle layer.
Pass `--timeout-ms 120000` (bounds Orca readiness/delivery wait, not task length); check `orca orchestration worker-show --dispatch <id>` and `orca orchestration worker-read --dispatch <id> --limit 20` (rows), continuing with `--cursor <cursor>`; output stays readable after worker-release. A worker that looks silent may be waiting on a question: check its inbox and worker-read and answer it. Never stop a worker for silence alone; report observed state. If worker-read shows an update prompt, tell the user to update Codex or answer the prompt; do not retry. If Orca is unavailable, report BLOCKED plainly and tell the user to start Orca; no fallback.
After a lost or uncertain mutation response, run `orca orchestration request-show --request <requestId>`. For completed/pending, repeat the SAME command with `--retry-request <requestId>` (replays the request, no second worker). Absent is not proof nothing happened: inspect `orca orchestration worker-show --dispatch <id>`, never start a duplicate. Do not duplicate accepted work after a timeout. Redo only a genuinely failed, settled worker with `orca orchestration worker-start --task <task_id> --retry-of <dispatch_id> --worktree current --agent codex --model codex-sub-model`.
Big job: use `--worktree new-child` lanes (max 4) for independent parts touching different files, serialize dependent/shared-file work, then use one integrator on `--worktree current` for linear history, separate review and release/worktree cleanup; see [Big job: parallel lanes](references/orca-usage.md#big-job-parallel-lanes).
On `agent_readiness` timeout, run `worker-show` once (the agent may still boot); if the brief never arrived, report BLOCKED with the observed state; no retry.
No test suite or fix-forward test loop. A toolkit release is confirmed with one quick direct check in a fresh session. Review/inceleme/kontrol requests remain readonly, not permission to mutate. Lead Read discovery is allowed; no scout prerequisite.

Before a live external operation using real credentials, ask the owner once for that target and record approval in the brief. Preserve project/tenant scope, redact secrets and report only observed evidence.
At task/milestone end, request worker facts; have the existing reviewer check Turkish claims too. Follow references/reporting.md; render approved text with references/render-report.mjs under /tmp and give the owner the HTML path. Keep unknown/not_run visible.
After a toolkit update, run /reload-plugins. See [Orca usage](references/orca-usage.md).
